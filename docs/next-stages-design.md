# Проект следующих этапов

Файлы не изменены. Ниже — предлагаемые решения для согласования. Работа приложения на S25 и Fold в рамках этого разбора не проверялась.

По коду есть три важных уточнения.

- ЛФК/йога уже дают образец последовательности шагов, голосовых переходов, камеры и сохранения прохождения. Их пороги завершения и награды требуют отдельных правил для силовых программ.
- `Workouts` записывает результат и награду одной транзакцией, повтор сохранения защищён `sessionId`. Этот механизм стоит сохранить.
- В `StatsMath` сейчас три характеристики. «Знание» потребуется добавить в перечисления, дневные итоги, кеш, расчёт уровня и интерфейс.

## Общая основа данных и синхронизации

Для всех этапов предлагаю следующие правила.

- **Новые факты** получают `uid, author, epoch, aseq`, доверенное время и учётные сутки. Связи между таблицами передаются через `uid`, как существующий `run_uid`.
- **Редактирование** создаёт новую версию записи. Удаление передаётся отдельным событием с идентификатором удаляемого объекта, чтобы восстановление копии сохранило результат удаления.
- **Шаблоны программ и продуктов** имеют неизменяемые версии. При одновременном редактировании на двух телефонах сохраняются обе версии для выбора владельцем.
- **Импорт фактов** обновляет историю и характеристики. Награду записывает телефон, принявший исходный результат, через существующий журнал кошелька.
- **Протокол обмена** расширяется вместе с `FactRecord`, кодеком, выборками `DiarySyncStore` и резервной копией. Сейчас неизвестный тип факта вызывает ошибку, версии протокола должны совпадать. Простое добавление таблицы обмен не обеспечит.
- **Проверка завершения этапа** включает повтор сохранения, обрыв обмена, восстановление копии и позднее получение фактов за уже закешированные сутки.

## 1. Домашние программы — L

### Данные

- `program_versions` — `program_uid, version_uid, title, builtin_id, parent_version_uid, rules_version`.
- `program_steps` — `version_uid, position, exercise_id, sets_count, target_reps/target_hold_ms, rest_ms, weight_kg`.
- `program_sessions` — `session_uid, version_uid, plan_snapshot, started_at, finished_at, status`.
- `program_set_links` — `session_uid, step_index, set_index, set_uid`.
- `program_finishes` — `session_uid, completed, active_ms, rest_ms`.

Фактические повторения и удержания остаются в `sets`. Определение программы фиксируется при старте. Завершённый подход сохраняется сразу с ключом вида `program:<session>:<step>:<set>`, чтобы закрытие приложения сохранило уже выполненную работу. Состояние текущего подхода — локальное, история завершённых подходов синхронизируется.

### Экраны и готовые программы

На главной — раскрывающийся раздел «Домашние тренировки», внутри готовые программы и «Мои программы». Конструктор позволяет выбрать упражнение, подходы, цель, отдых и гирю.

Стартовые шаблоны для последующей проверки камерой и подбора нагрузки владельцем.

| Программа | Состав |
|---|---|
| «Новичок, всё тело, ≈20 мин» | Приседания 3×10, отжимания 3×6, пресс 3×10, планка 3×20 с, отдых 45–60 с |
| «Ноги и кор» | Приседания 3×12, пресс 3×10, планка 3×30 с, отдых 45–60 с |
| «Гиря — силовая» | Присед у груди, становая тяга, жим, тяга к поясу — по 3×10, отдых 60–90 с |
| «Гиря — выносливость» | Махи 4×20, трастер 3×10, присед у груди 3×12, отдых 30–45 с |

Продолжительность рассчитывается приблизительно. Потеря распознавания и перестановка телефона увеличивают время.

Во время занятия — техника из `guide/*`, цель подхода, камера, следующий шаг. После достижения цели запускается отдых с голосом. Перед новым упражнением показывается нужный ракурс и ожидается готовность камеры. Кнопки паузы, сокращения отдыха и пропуска управляют последовательностью.

### Награды и характеристики

- Каждый подтверждённый подход оплачивается по `Exercises.rewardMs` или `holdRewardMs`, включая частично выполненный.
- **Предлагаю стартовать с нулевого бонуса минут за завершение.** Пользовательский шаблон из одного повторения иначе становится способом получать бонус.
- Сила — по существующим правилам. Сейчас для повторений нужен хотя бы один подход от 10 повторений за день, рабочий потолок — 8 очков.
- Для новых программ предлагаю первоначально нулевой бонус `COMPLEX_DONE`. Иначе короткие пользовательские программы позволят получать дополнительные очки силы.
- Время отдыха даёт 0 выносливости. Для домашних программ предлагаю сначала учитывать только обычные источники силы, отдельные очки выносливости согласовать позже.

### Камера и лазейки

Камера подтверждает цикл движения и удержание позы. Масса гири остаётся заявленной владельцем, существующие множители 16/24/32 кг имеют эту же уязвимость. Возможны показ записи перед камерой, неполная амплитуда и повторный счёт после восстановления экрана. Нужны сохранение идентичности подхода, сброс незавершённого цикла при потере человека и проверка каждого упражнения на устройстве.

**Спросить владельца** — подходят ли четыре шаблона, какие гири используются, принимать ли нулевой бонус за программу и сохранять ли порог силы «один подход от 10».

## 2. Зал — L для первых упражнений

### Честный вариант

**Предлагаю запускать подтверждаемый зал по одному упражнению.** Первый кандидат выбирается после съёмки реального ракурса — присед со штангой, жим лёжа сбоку или тяга.

При недоступной камере допустимы каталог оборудования, план тренировки и выбранный вес. Фактические повторения появляются после распознавания камерой.

Вариант «вручную записывать вес и сделанные повторения, начислять 0 минут» требует изменения решения владельца о запрете ручного результата. При действующем решении полноценная история выполненных подходов на всех тренажёрах технически недостижима.

### Данные и экраны

- `gym_exercises` — `exercise_uid, name, equipment_type, camera_profile_id, verification_status`.
- `gym_load_entries` — `exercise_uid, equipment_uid, time_ms, load_grams, load_mode, purpose`.
- `gym_set_details` — `set_uid, exercise_uid, equipment_uid, declared_load_grams, detector_version`.

`purpose` различает планируемый вес и вес, привязанный к подтверждённому подходу. `load_mode` определяет общий вес штанги, вес одной гантели или отметку стека. Все пользовательские записи синхронизируются.

Экраны — каталог зала, настройка веса и камеры, подход, история упражнения. В «Прогрессе» — рабочий вес при одинаковом числе подтверждённых повторений, фильтр по конкретному тренажёру и способу учёта веса.

### Награды, камера и риски

- Подтверждённые повторения могут давать силу по обычным правилам.
- Предлагаю фиксированную цену повторения для упражнения. Множитель заявленного веса создаёт прямую возможность завысить награду.
- Записи выбранного веса дают 0 минут и 0 очков характеристик.
- Камера проверяет доступную ей кинематику. Для штанги и тренажёров нужны собственные проверенные профили распознавания.
- Главные риски — перекрытые суставы, чужие люди, движение страхующего, неверная привязка человека, различия тренажёров и заявленный вес.

Для новых упражнений нужны гиды с конкретным ракурсом и условиями зачёта.

**Спросить владельца** — первое упражнение и доступный ракурс, список оборудования, способ записи веса гантелей, приемлема ли оплата без множителя массы.

## 3. Питание — L целиком

Разделить на фото — M и продукты со штрихкодами — M.

### Данные

- `meal_events` — `meal_uid, captured_at, accounting_day, zone_id`.
- `meal_photos` — `meal_uid, blob_hash, width, height, bytes, mime`.
- `product_versions` — `product_uid, version_uid, barcode, name, label_photo_hash, nutrients_per_100g, default_portion_g`.
- `meal_products` — `meal_uid, product_version_uid, portion_g`.
- Исправления и удаления — отдельные синхронизируемые события.

Окно питания вычисляется по первому и последнему зафиксированному приёму за учётные сутки. При единственной записи показывается «Один приём». Между полуночью и утром применяется общий учётный пояс приложения.

### Экраны и подтверждение

Лента по дням, съёмка внутри приложения, просмотр фото, окно питания, затем сканер и свои продукты. Время снимка ставится автоматически.

Камера подтверждает наличие сделанного снимка. Приём пищи, полноту дневника, состав и массу порции она не устанавливает. Минуты и очки характеристик — 0. Пропуск фотографии способен искусственно сократить окно, поэтому показатель подписывается как окно **зафиксированных** приёмов.

### Фото, обмен и копия

- Постоянные изображения — во внутреннем `filesDir`, уменьшенные превью — в кеше. В SQLite хранятся метаданные и хеши.
- Предлагаемый размер — длинная сторона 1600 px, JPEG с ориентиром 200–500 КБ. При пяти фото в день получится примерно **0,37–0,91 ГБ в год на каждом телефоне**.
- Сначала синхронизируются метаданные, затем недостающие файлы по SHA-256. Передача порциями с возобновлением и финальной проверкой хеша. Сейчас сообщение обмена ограничено 1 МиБ.
- Настройка по умолчанию — полные фото на обоих телефонах при встрече по Wi‑Fi. В интерфейсе видны очередь, объём и нехватка места.
- Резервная копия расширяется манифестом изображений и файлами. Текущая копия содержит базу и настройки. Перед экспортом показываются отсутствующие фото и итоговый размер. Восстановление проверяет хеши и безопасные пути архива.

Для полностью автономного сканирования выбрать ML Kit с моделью, включённой в APK. Штрихкод используется как ключ своей карточки продукта. [Документация ML Kit](https://developers.google.com/ml-kit/vision/barcode-scanning/android)

**Спросить владельца** — полные фото на обоих устройствах, приемлемый годовой объём, нужны ли порции и БЖУ уже в первой версии, нужна ли защищённая паролем копия.

## 4. Карточки — M

### Данные и синхронизация

- `deck_versions` — `deck_uid, version_uid, title, subject`.
- `cards` — `card_uid, deck_version_uid, prompt, accepted_answers, direction`.
- `card_attempts` — `attempt_uid, card_uid, content_version, presented_at, answered_at, day, first_correct, reward_ms`.
- `card_schedule` — производный кеш `due_at, interval_days, streak, lapses`.

Попытки — неизменяемые синхронизируемые факты. Расписание пересчитывается из их общей истории.

**Для первой версии предлагаю один назначенный телефон карточек**, выбираемый владельцем. Он принимает оплачиваемые попытки и обеспечивает общий потолок 300 секунд. Переключение телефона — после синхронизации, передающей историю и право начисления. Одновременная автономная оплата на двух телефонах потребует отдельного распределения квоты.

### Колоды, ответы и повторение

- Английские слова — небольшая собственная колода с однозначными заданиями, исходно 100–300 слов.
- Таблица умножения, затем сложение и вычитание с заданным диапазоном.
- Счёт — цифровая клавиатура. Слова — текстовый ввод с допустимыми вариантами и нормализацией регистра и пробелов.
- Ответ фиксируется одной отправкой. После ошибки раскрывается решение и назначается повтор.
- Начальная схема интервалов — 1, 3, 7, 14, 30 дней. Ошибка возвращает карточку на короткий интервал. Повтор в той же сессии служит закреплению.

### Награды и «Знание»

- 10 секунд за правильную первую попытку, максимум 30 оплачиваемых ответов за сутки.
- Одна карточка оплачивается максимум один раз за сутки. Просмотр подсказки делает текущую попытку неоплачиваемой.
- Используется существующий `OpKind.CARD_REWARD`, ключ — `card:<attempt_uid>`. Попытка и начисление записываются одной транзакцией.
- Предлагаемое «Знание» — 1 очко за каждые 3 различных правильных первых ответа, до 10 за день. Штраф за простой первоначально 0.
- Восстановление копии должно сохранять уже оплаченные попытки и использованную квоту текущего дня.

Камера здесь не участвует. Варианты из четырёх дают 25% случайных попаданий. Ввод ответа уменьшает угадывание, остаются заучивание короткой колоды, подсказки извне и автозаполнение. Новые оплачиваемые задания выдаются из очереди приложения.

**Спросить владельца** — предмет, уровень английского или диапазон счёта, телефон карточек, предлагаемая формула «Знания».

## 5. «Режим столика» Fold — M

### Модель и экран

Новых таблиц фактов не требуется. Настройка включения режима хранится локально, результаты проходят через обычные `sets` и прохождения программ.

Дополнить `Adaptive.kt` сведениями из `WindowLayoutInfo`. Условие режима — горизонтальный сгиб `FoldingFeature` в состоянии `HALF_OPENED`. Размещение учитывает реальные границы сгиба и свободные области окна. [Документация Android](https://developer.android.com/guide/topics/large-screens/foldables)

- Верхняя половина — превью камеры, скелет и подсказка положения.
- Нижняя — крупный счётчик, цель, отдых, следующее упражнение и основные действия.
- Общая раскладка применяется к упражнениям, планке, комплексам и новым программам.

### Правила и риски

Цены и характеристики следуют обычным правилам упражнения. Камера подтверждает те же движения и удержания.

Основная работа — сохранение идентичности подхода при складывании, перепривязке CameraX и изменении размеров. После прерывания распознавания счётчик начинает новый цикл движения от исходного положения. Нужно проверить наклон фронтальной камеры, обрезку тела, зеркальность и трансформацию скелета на настоящем Fold.

**Спросить владельца** — удобное положение Fold относительно тела, расстояние и предпочтительные кнопки нижней половины.

## 6. Обновления из GitHub — M

### Данные и экраны

Локальное состояние `update_state` — время проверки, ETag, версия, `release_id`, `asset_id`, размер, ожидаемый SHA-256, путь загрузки, статус и идентификатор сессии установщика. Синхронизация между телефонами для этих данных не требуется.

В настройках — установленная версия, «Проверить обновление», описание релиза, размер, загрузка и установка. Награды и характеристики — 0, камера не участвует.

### Получение и установка

- Проверять `/repos/RjMilk/next-level-life/releases/latest` при открытии приложения с интервалом порядка суток и по кнопке. Лимит без токена — **60 запросов в час на исходящий IP**, общий для телефонов за одним роутером. Учитывать кеш, ETag и ответы ограничения частоты. [Лимиты GitHub](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- `latest` пропускает prerelease. Если отладочные APK публикуются с этой отметкой, понадобится список релизов и отдельное правило выбора канала. Сравнивать установленный `versionCode` с версией APK. [API релизов](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)
- Скачивать APK во внутреннее временное хранилище, проверять размер и SHA-256 из ассета контрольных сумм. Дополнительно можно сверять `digest` из API. [Ассеты релиза](https://docs.github.com/en/rest/releases/assets)
- До установки проверять криптографическую подпись APK, доверенный сертификат, `applicationId` и возрастающий `versionCode`.
- Объявить `REQUEST_INSTALL_PACKAGES`, проверить разрешение источника через `canRequestPackageInstalls()`, затем использовать сессию `PackageInstaller`. Обрабатывать системное подтверждение, отмену, недостаток места и все итоговые статусы. [Разрешение источника](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls()), [PackageInstaller](https://developer.android.com/reference/android/content/pm/PackageInstaller)

### Подпись и подмена

SHA-256 из того же релиза защищает целостность загрузки. При захвате GitHub-аккаунта атакующий сможет заменить APK и файл хеша. Поэтому доверие опирается также на **заранее известный сертификат подписанта**, закрытый ключ хранится отдельно от публичного репозитория.

В текущем Gradle-файле явная постоянная конфигурация подписи отсутствует. Предлагаемый порядок.

1. Сверить сертификаты установленных APK на S25 и Fold и найти соответствующие закрытые ключи.
2. Если ключ общий и сохранён, закрепить его для публикуемых сборок.
3. Если ключи разные, подготовить переход каждой установки на общий ключ. При наличии старых ключей проверить подписанную цепочку ротации на обоих устройствах. При утрате ключа потребуется перенос через проверенную резервную копию.
4. Хранить постоянный keystore и его резервную копию приватно. Сборки на разных компьютерах должны использовать согласованную подпись.

Режим debug совместим с обновлениями при соблюдении требований подписи. Отдельный остаточный риск — доступность отладки в опубликованной сборке. [Подпись приложений Android](https://developer.android.com/studio/publish/app-signing)

Для России проверить API, перенаправления и скачивание ассетов на обеих сетях владельца. При сетевом сбое сохранять состояние загрузки и возможность повторить операцию.

# Порядок и параллельная работа

Рекомендуемый порядок выполнения.

1. **Закрепить ключ подписи**, спроектировать расширение фактов, версий протокола и резервной копии.
2. **Домашние программы** — готовые шаблоны и прохождение, затем конструктор.
3. **Фото питания**, затем штрихкоды и продукты.
4. **Карточки** после согласования единственного источника начисления и «Знания».
5. **Зал** после испытания первого упражнения камерой.

«Режим столика» и интерфейс обновления можно вести параллельно со вторым этапом.

| Независимая часть | Предлагаемые файлы и области |
|---|---|
| Домашние программы | `data/Programs.kt`, `data/ProgramWorkouts.kt`, `ui/ProgramScreen.kt`, `ui/ProgramEditorScreen.kt` |
| Питание | `data/Nutrition.kt`, `media/*`, `ui/NutritionScreen.kt` |
| Карточки | `data/Cards.kt`, `data/CardMath.kt`, `ui/CardsScreen.kt` |
| Fold | `ui/Adaptive.kt`, отдельная общая раскладка камеры и табло |
| Обновления | `update/*`, `ui/UpdateScreen.kt` |
| Зал | `data/Gym.kt`, `pose/GymCounters.kt`, `guide/GymGuides.kt`, `ui/GymScreen.kt` |

Общие изменения в `Diary.kt`, `Workouts.kt`, `LedgerMath.kt`, `StatsMath.kt`, `sync/*`, `Backup.kt`, `HomeScreen.kt`, навигации и Gradle стоит интегрировать последовательно. Сначала согласовать поля и интерфейсы, затем подключать готовые части.
